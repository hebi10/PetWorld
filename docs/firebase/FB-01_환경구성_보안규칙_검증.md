## 2. Firestore 규칙 — 실제 동작 기준

- `users/{uid}`: 본인 인증 사용자에 한해 get/create/update, list 불허, 물리 삭제 차단. `migrationState`와 최초 작성시각·revision 필수.
- `users/{uid}/pets/{petId}`: 본인만 읽기·생성·수정 가능. ID·자료형·필수 필드·허용 키·revision(+1) 검증.
- `users/{uid}/pets/{petId}/records/{recordId}`: 본인만 읽기·생성·수정. 부모 프로필이 존재해야 생성 가능; 필수 필드·enum·숫자·revision 검사.
- 다른 `uid`, 인증되지 않은 사용자, 정의되지 않은 경로·추가 필드, client document delete 전부 차단.
- **보안상 중요한 한계:** revision은 클라이언트 트랜잭션 충돌 보호의 바탕일 뿐 서버에서 신뢰하는 정산·권한/요금 로직이 아니다. 동시 수정 해결/원격 삭제 tombstone은 FB-05에서 구현.
- 스키마 키는 FB-00의 Room 매핑을 기반으로 한 **초기 보안 계약**이다. 원격 사진 참조·동기화 메타데이터의 최종 계약은 FB-04~FB-06에 근거해 변경·테스트해야 한다.
- Security Rules는 웹/Android 클라이언트 요청에 적용되며 Firebase Admin SDK의 서버 권한을 대체하지 않는다. 서버 계정에는 별도 IAM 최소 권한이 필요하다.

## 3. Storage 규칙 — 실제 동작 기준

- 경로: `users/{uid}/pets/{petId}/photos/pet_<UUID>.jpg`, 인증 사용자 본인만 `get`, 유효 JPEG의 **최초 업로드(create)** 가능.
- 제한: `image/jpeg`, 1바이트 이상 5MiB 이하, 기존 `pet_<uuid>.jpg` 파일명, `uid` 경로 일치.
- `list`, `update`, `delete`는 FB-06의 사진 참조·중복/정리 정책이 확정되기 전 **의도적으로 차단**.
- JPEG의 MIME만 확인하며 **실제 파일 내용 디코딩·악성파일 검사·사용자별 총량 제한은 규칙만으로 보장되지 않는다**. FB-06에서 검증 및 백엔드 제한 보강.
- 업로드 사진과 Firestore 프로필 존재 관계의 동시 검증도 FB-06로 보류. 클라이언트는 원격 저장 경로와 일회성 download URL을 혼동하지 않도록 설계.

## 4. 로컬·CI 검증 실행

Node.js 22·Java 21 준비 후 저장소 루트에서:

```bash
npm install --prefix firebase --no-audit --no-fund
./firebase/node_modules/.bin/firebase emulators:exec --project demo-petworld-fb01 --only firestore,storage --config firebase.json --non-interactive "npm --prefix firebase run test:rules"
```

- `demo-*` ID는 실제 Google Cloud 리소스를 만들지 않는 Firebase Emulator 용도이며 Firebase 계정에 로그인하지 않는다.
- GitHub Actions는 `firebase/**`, `firebase.json`, 해당 workflow 변경 PR에서 동일 검사를 수행.
- CI는 시크릿이나 `google-services.json` 없이 실행 가능. 실제 Firebase Auth·Cloud Firestore/Storage에 연결하지 않는다.
- Android CI·Play exact-source 검증은 동일 FB-01 HEAD에서 별도로 확인한다. Firebase Emulator 성공은 실제 Play 로그인 성공을 증명하지 않는다.

## 5. Firebase 프로젝트 설정 결정·대기

### 개발/운영 분리
- 권장: PetWorld 개발/테스트 프로젝트와 운영 프로젝트 분리. **실제 프로젝트 이름/ID 및 결제 계정은 추정·생성하지 않는다.**
- Android 앱 등록은 **반드시** `com.haebi.petworld`로. 프로젝트 구성 시 등록된 Android 패키지명과 Play 서명 SHA-1/256을 확인한다.
- 개발 프로젝트도 앱 서명키/업로드키를 혼동하지 않는다. Android OAuth/Google 로그인에는 배포 인증서의 SHA가 필요하다.
- `google-services.json` 파일은 실제 Firebase Console에서 내려받고 `.gitignore`에 의해 저장소에서 제외한다.
- `google-services.json`/Google Services Gradle plugin 및 Auth 의존성·`INTERNET` 권한 추가는 **실제 Android 앱 등록 및 정책 변경 기준을 확인한 후 FB-02에서 구현**한다.
- 절대로 Firebase Admin SDK 서비스 계정 JSON/개인키를 Android 앱이나 PR에 포함하지 않는다.

### 데이터 위치
- Firestore 리전 후보 `asia-northeast3`(서울): 국내 사용자의 지연 및 운영 관점을 고려.
- Storage 버킷 위치는 Firestore 위치와 **독립적으로** 선택된다. 버킷 생성 전에 지원 위치·전송/저장 단가를 별도 확인.
- Cloud Firestore 기본 DB 위치 결정 후 이동이 어렵다. 사용자 승인·요금 검토 이전 생성 금지.

### 요금·결제
- Cloud Storage for Firebase는 **Blaze(종량제) 요금제**가 필요하므로 결제 계정 연결 전 예상 사용량·예산 경보/분석을 문서화한다.
- Blaze의 무료 사용량은 버킷 위치·서비스에 따라 달라질 수 있다. 서울 리전에서 미국 지역 Always Free 수치를 무조건 적용하지 않는다.
- Firebase 결제 예산 알림만으로 자동 과금 중지된다고 표현하지 않는다.
- 이번 PR에서는 실프로젝트·버킷·Firebase Auth·App Check·Google Play 설정 및 요금제 변경 **없음**.
