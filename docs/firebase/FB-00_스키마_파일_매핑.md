# FB-00 — Room ↔ Firebase 데이터·파일 매핑 명세

- 상태: 제안 스키마 / 구현 전
- 확인된 소스: `app/src/main/java/com/haebi/petworld/data/room/PetWorldDatabase.kt` 및 `data/*Repository.kt`, `data/backup/*`
- Git 기준선: `a618de146215ee7b2447b433022e2b5d7e85130a`
- 기존 DB: `petworld_profiles.db`, Room version 2, 기존 1→2 비파괴 마이그레이션 `MIGRATION_1_2`
- 기존 백업: `.petworld` 암호화 파일, `formatVersion=1`, `schemaVersion=2`. Firebase 적용 뒤에도 호환 유지

## 1. 원격 컬렉션 경로 — FB-04에서 구현 예정

```text
users/{uid}                              # 인증된 계정/이행 상태(최소 메타데이터)
users/{uid}/pets/{petId}                 # 현행 pets 1개당 1문서
users/{uid}/pets/{petId}/records/{id}    # 현행 care_entries 1개당 1문서
users/{uid}/syncMetadata/{deviceId}      # 서버 커서·리비전(설계 후 확정)
```

- 클라이언트는 인증된 `uid`만 접근할 수 있도록 Firestore Security Rules에서 강제한다.
- `petId`·`id`는 **기존 UUID 문자열을 그대로 사용**한다. 원격 전송 시 새로운 UUID를 생성하지 않는다.
- 문서에는 `schemaVersion`, 서버 검증 리비전, 생성·변경 시각, 삭제 플래그 등 동기화 전용 메타데이터를 추가하되 현행 Room 도메인 필드는 변경하지 않는다.
- `uid`·`deviceId`를 쿼리 문자열이나 공개 로그로 출력하지 않는다.
- 가족 공유는 FB-10에서 별도 Household 경로·권한 모델로 확장한다. 초기 개인 소유 경로를 임의 공동 소유로 처리하지 않는다.

## 2. `pets` / `PetEntity` 필드 매핑

| Room Entity 속성 | 저장 형식 | 제안 Firestore 문서 | 보존 규칙 |
| --- | --- | --- | --- |
| `id` | String UUID PK | `pets/{petId}` 문서 ID + `id` | 변경 금지 |
| `name` | String | `name` | 빈 값/길이 현행 검증 재사용 |
| `species` | String | `species` | 기존 enum 저장값 그대로 |
| `breed` | String | `breed` | 빈 문자열/결측 변환 금지 |
| `birthday` | String? | `birthday` | null 보존 |
| `estimatedAgeYears` | Int? | `estimatedAgeYears` | null/정수 보존 |
| `sex` | String | `sex` | 기존 값 보존 |
| `neuterStatus` | String | `neuterStatus` | 기존 값 보존 |
| `notes` | String | `notes` | 문자열과 길이 검증 보존 |
| `photoFile` | String? | `photoRef.localName` + `photoRef.storagePath` | 기존 JPG 이름은 로컬에서 유지; Storage 업로드는 분리 |
| `isArchived` | Boolean | `isArchived` | 보관은 삭제와 구분 |
| `createdAt` | Long (epoch ms) | `createdAtMs` | 밀리초 정수 보존 |
| `updatedAt` | Long (epoch ms) | `updatedAtMs` | 기기 시각=충돌 승자 기준으로 사용 금지 |

- 서버 추가 필드(제안): `schemaVersion=1`, `revision`, `serverUpdatedAt`, `deletedAt`, `lastOpId`.
- 원격 저장 경로와 `localName`의 대응은 별도 사진 매핑 테이블/구조로 명시한다. 단일 원격 `photoFile` 필드로 로컬 파일 경로를 덮어쓰지 않는다.

## 3. `care_entries` / `CareEntity` 필드 매핑

| Room Entity 속성 | 형식 | 제안 Firestore 속성 | 원칙 |
| --- | --- | --- | --- |
| `id` | String UUID PK | 문서 ID + `id` | 변경 금지 |
| `petId` | String FK | `petId` | 부모 문서 `petId`와 일치 검증 |
| `type` | String | `type` | 식사/음수/배변/활동/체중 저장값 |

| `timezoneId` | String | `timezoneId` | 시간대 문자열 원본 유지 |
| `foodKind` | String? | `foodKind` | null 보존 |
| `foodProductName` | String? | `foodProductName` | null/빈 문자열 구분 |
| `foodServedMilli` | Long? | `foodServedMilli` | g·mL 혼합 합산 금지 |
| `foodConsumedMilli` | Long? | `foodConsumedMilli` | 미측정 null vs 측정 0 구분 |
| `foodUnit` | String? | `foodUnit` | g/mL 원본 보존 |
| `waterMl` | Long? | `waterMl` | null/0 구분 |
| `eliminationKind` | String? | `eliminationKind` | 소변/대변 기존 값 |
| `eliminationCount` | Int? | `eliminationCount` | null/정수 보존 |
| `activityKind` | String? | `activityKind` | 기존 산책/놀이/수면/기타 |
| `activityMinutes` | Int? | `activityMinutes` | 정수 분 유지 |
| `weightGrams` | Long? | `weightGrams` | g 정수 보존 |
| `weightInputUnit` | String? | `weightInputUnit` | kg/g 입력 단위 보존 |
| `photoFile` | String? | `photoRef.localName` + `photoRef.storagePath` | 선택 사진 참조 유지 |
| `note` | String | `note` | 최대 글자 수 현행 정책 검증 |
| `createdAt` | Long | `createdAtMs` | 작성 시각 보존 |
| `updatedAt` | Long | `updatedAtMs` | 수정 시각 보존 |

- 클라우드에는 `schemaVersion`, `revision`, `serverUpdatedAt`, `deletedAt`, `lastOpId` 등 복제 메타데이터 추가 가능.
- Firestore Long/Int를 Float/Double로 임의 변환하여 정밀도가 손실되지 않도록 Kotlin 인코더와 서버 문서의 정수 범위를 테스트한다.
- `occurredAt` + `timezoneId`를 유지한다. Firestore Timestamp를 추가 사용하더라도 원본 millisecond/timezone을 잃지 않도록 할 것.
- 물리적으로 삭제된 부모 프로필의 `care_entries`는 기존 FK CASCADE에 따라 로컬에서 제거되지만, 클라우드에서는 tombstone과 별도 삭제 작업으로 일관성을 보장해야 한다.

## 4. 사진 Storage 경로·무결성 매핑

```text
로컬 비회원: {filesDir}/pet_photos/pet_<UUID>.jpg
로컬 로그인: {filesDir}/{accountScope}/pet_photos/pet_<UUID>.jpg   # 제안, FB-03에서 안전한 실제 경로 확정
원격: users/{uid}/pets/{petId}/photos/{photoId}.jpg
```

- 로컬 사진은 기존 `PetPhotoStore.importPhoto`를 통해 저장된다. 앱 내부 경로는 외부 유효 `content://` URI와 별개다.
- `photoId`는 원격 객체 고유 ID, `photoFile`은 기존 로컬 JPG의 이름; 둘의 매핑을 명확히 유지한다.
- `PhotoRef` 제안: `localName`, `storagePath`, `sha256`, `contentType`, `byteLength`, `syncState`.
- Cloud Storage 객체 업로드 후 `sha256`·크기 등 무결성을 검증한 시점에만 Firestore 참조를 확정한다.
- 이전 사진은 새 파일 업로드 및 모든 필요한 참조 변경 전까지 삭제하지 않는다.
- Storage Rules: `request.auth.uid == uid`를 기본으로 파일 크기·콘텐츠 유형·소유 관계 검증. 공개 링크를 영구 식별자로 저장하지 않는다.
- 현재 계정 없는 로컬 사진은 기존 앱 샌드박스에서 보존; 로그인 취소로 삭제하지 않는다.
- 타 계정 전환 시 이전 계정 로컬 이미지/캐시가 새 사용자에게 노출되면 안 된다.

## 5. DataStore / 백업 파일 매핑

| 현재 데이터 | 로컬 기준 | 클라우드 기본 정책 |
| --- | --- | --- |
| `theme_mode` | 전역 사용자 UI 설정 | 초기에는 동기화 대상에서 제외; 기존 DataStore 유지 |
| `selected_pet_id` | 비회원 또는 해당 계정별 선택 값 | 계정별 로컬로 분리; 서버 저장 필요성 FB-03에서 최종 검토 |
| `.petworld` 백업 | 계정 없는 기존 파일도 지원 | 수동 복구 수단으로 보존, 자동 클라우드 양방향 복제물로 사용하지 않음 |
| `petworld_restore_journal` | `noBackupFilesDir`의 pending/이전 백업 | 서버에 업로드하지 않음; 계정별 복구 원자성·잠금 검토 |

- 현재 백업 Exporter는 Room 트랜잭션으로 `pets`/전체 `care_entries` 스냅샷을 얻고, 사진 및 설정과 ZIP→AES-GCM 암호화 스트림을 생성한다.
- Restorer는 포맷·SHA·사진·FK 등을 검증한 후 **현재 선택 DB의 전체 데이터를 교체**한다. 계정 스코프 DB 선택과 서버 동기화 중지 없이 실행 금지.
- 기존 백업의 `formatVersion=1`, `schemaVersion=2`는 향후 변환을 추가해도 읽을 수 있어야 한다.
- 암호화 백업을 만들었다는 것만으로 Play Console 데이터 보안/클라우드 E2EE가 충족되는 것은 아니다.

## 6. 동기화 메타데이터·outbox 초안(기존 Room v2에는 없음)

| 구분 | 필드 후보 | 역할 |
| --- | --- | --- |
| `sync_outbox` | `op_id`, `account_scope`, `entity_id`, `entity_kind`, `action`, `base_revision`, `state`, `attempts`, `enqueued_at` | 재시도·중복 방지 |
| `sync_cursor` | `account_scope`, `collection`, `cursor`, `last_checked_at` | 증분 다운로드 |
| `sync_conflicts` | `entity_id`, `local_revision`, `remote_revision`, `resolution_state` | 충돌 보존·해결 |
| `photo_sync` | `local_name`, `storage_path`, `sha256`, `byte_length`, `state` | 사진 전송·보존 |
| 서버 문서 | `revision`, `serverUpdatedAt`, `lastOpId`, `deletedAt` | 경쟁 상태·삭제 동기화 |

- 위 테이블은 **제안**일 뿐, 현재 Room v2에 존재하지 않는다. 실제 버전 증가/필드 정의는 FB-03~06의 개별 마이그레이션과 테스트로 반영한다.
- WorkManager의 작업 이름/재시도는 반드시 계정 스코프에 묶는다.
- Firestore 하위 컬렉션의 청소·권한 제한·탈퇴 삭제는 별도 서버 측 처리 절차가 필요하다.

## 7. 무손실 데이터 검증 계약

1. 비회원 데이터에서 `petId`/기록 `id` 집합, 동물별 기록 수, 수치·NULL·타임존, 사진 파일 SHA-256을 추출.
2. 사용자 확인 후 **복사본**에서 이행. 비회원 원본 `petworld_profiles.db`/사진은 변경하지 않는다.
3. 계정 전용 Room으로 가져온 뒤 FK 무결성·건수·바이트 해시·선택 반려동물 ID 확인.
4. Cloud 저장 중 중단/중복 재시도는 `id`와 `opId`로 멱등 처리. 같은 ID의 다른 데이터는 사용자 충돌 확인 전 보존.
5. 서버 readback 검증을 거친 뒤에만 동기화 완료 표시. 통신 오류 시 부분 업로드 정보를 저장해 재개.
6. 로그아웃·다른 계정 연결 전 outbox/동기화 작업 정지, 기존 계정 DB/사진 UI 정리.
7. 기존 `.petworld` 백업 생성·복원을 새 구현 전후에 비교하여 원래의 모든 값을 잃지 않는지 검증.
