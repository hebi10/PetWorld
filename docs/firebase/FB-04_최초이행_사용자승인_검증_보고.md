# FB-04 — 기존 비회원 기록의 Firebase 최초 이행

기준일: 2026-11-12 / PetWorld / Google Drive FB-04 기획 기반
선행: Draft PR #27 → #28 → #29 → #30 → #31 → #33 → #34 → #35
**Firebase 기능 개발 중에는 Google Play 배포 금지. FB-09 최종 통합 QA 및 명시적 GO 이후 한 번 배포.**

## 1. 실제 데이터와 서비스 범위

- Guest: 기존 `petworld_profiles.db` Room v2의 `pets`/`care_entries`와 `pet_photos` JPEG 파일, DataStore `selected_pet_id` 사용.
- 계정: `firebaseDev`에서 `petworld-dev / com.haebi.petworld.dev`가 일치하고 FirebaseAuth로 실제 로그인된 경우만 후보.
- 원격 Firestore: `users/{uid}`, `users/{uid}/pets/{petId}`, `users/{uid}/pets/{petId}/records/{recordId}`. 생성 시 revision=0, 기존 원격 문서는 사용자 승인 없이 절대 overwrite하지 않음.
- 원격 Storage: `users/{uid}/pets/{petId}/photos/pet_<uuid>.jpg`, contentType=image/jpeg, 용량 5 MiB 이하, 최초 생성만 허용.
- Firestore 기존 Rules에 없는 필드/경로로 사용자 데이터가 전송되지 않도록 현행 `firebase/firestore.rules`, `firebase/storage.rules`의 허용 스키마를 그대로 따름. Firebase 원격 Rules 자체는 이 PR에서 배포·수정하지 않음.
- Room의 사진 참조 `photoFile`은 파일명만 보존. 원격 Storage 경로는 해당 UID·petId·파일명으로 파생. 사진이 서버에 존재·일치하기 전 문서 참조가 작성되지 않게 순서를 제어.

## 2. UI 승인 및 사전 점검

1. 개발 계정 화면에서 Google 계정 로그인 후 `기기 기록·클라우드 상태 확인` 클릭: 읽기 전용 미리보기만 실행하며 **쓰기 요청 없음**.
2. Guest DB에서 pet/record UUID, 모든 숫자(0/null 포함), 작성/수정/발생 시각·timezone, 선택 프로필 읽기; FK와 원격 Rules 제약 검증.
3. Guest 로컬 JPG 참조 목록·파일 존재·5 MiB 한도·SHA-256 점검. 5MiB 초과/누락/이름 불일치 시 실패하며 사진을 잘라서 변경하지 않음.
4. Firestore 서버 조회(Source.SERVER) 및 Storage 실제 byte SHA를 비교. 동일 ID·같은 내용이면 기존 항목 재사용, 같은 ID·다른 내용이면 **충돌**로 중단. 클라우드에만 있는 추가 기록은 개수를 표시.
5. 사용자는 사전에 설정에서 암호화 `.petworld` 백업을 만들어 보관한 뒤 해당 완료 여부를 **명시적으로 체크**하고 다시 확인해야 함. 앱은 체크 여부만 확인하며 실제 외부 백업 파일의 존재는 검사하지 않음.
6. 서버에 기기 외의 기록이 이미 있는 경우 `기존 데이터 유지·새 항목만 추가` 별도 체크 필요. 사용자가 취소하면 원격 및 로컬 데이터 변경 없음.
7. 미리보기 원본 SHA-256을 저장하지 않고 화면 상태에 유지. 복사 시작 시 Guest DB/사진을 다시 읽어 같은 지문인지 검사. 변경됐으면 중단하고 재미리보기.

## 3. 실제 이전 및 재시도

1. 시스템 공통 `PetWorldMutationGate`를 사용해 최초 이전 중 Guest 프로필·기록·사진의 앱 내 동시 수정을 보류. 외부 수정이 발생해 원본 해시가 달라지면 중단.
2. 사진 파일을 Storage에 먼저 업로드, SHA-256을 사용자 메타데이터에 추가. 이미 존재하는 사진은 **서버에서 실제 파일 bytes를 내려받아 해시 비교**해 같은 경우에만 재사용. 차이 있으면 덮어쓰기 없이 중단.
3. 사용자 문서 `users/{uid}` 없을 때 schemaVersion=1 / migrationState=pending / revision=0으로 생성. 기존 있으면 덮어쓰지 않음.
4. 각 pet/record를 고정 UUID로 1문서씩 Firestore Transaction(`get`→`set` create-only) 처리. 기존 doc 동일하면 건너뛰고, 조금이라도 다르면 충돌로 중단; 레코드는 부모 pet 문서 존재 후 생성.
5. **서버 별도 재조회**로 pet/record 필드·사진 bytes/해시 일치 및 Guest 로컬 자료 해시 재검증 후에만 user migrationState=ready(리비전 증가)로 바꾸고 완료를 화면에 표시.
6. 네트워크 중단·프로세스 종료 등으로 일부 서버 항목이 생성됐더라도 Guest 데이터는 삭제하지 않음. 사용자가 재미리보기→재승인하면 동일한 항목은 idempotent로 건너뛰며 나머지만 추가.
7. 비회원 DB/사진을 계정 Room으로 자동 이관하지 않고 Firestore로만 원본 자료의 **첫 보관**을 수행한다. 계정 로컬 캐시 복구/양방향 동기화는 FB-05 후속 단계.
8. SharedPreferences `petworld_fb04_import`에는 계정 해시 키와 소스 fingerprint만 저장하여 재시도 진단에 사용. 비밀번호·토큰·UID 원문·기록 내용은 저장하지 않음.

## 4. 보존·충돌·한계

- 충돌 난 기존 클라우드 문서를 삭제·덮어쓰지 않음. 충돌의 상세 선택·병합 편집 기능은 후속 UI/FB-05에서 확장 예정.
- PhotoFile이 5MiB 초과/유효하지 않은 경우 업로드 불가 상태를 표시; 로컬 원본은 그대로 두고 수동 해결 후 재실행.
- 동일 사진이 여러 반려동물에게 참조된 경우 Storage의 petId별 경로로 별도 업로드하며 UUID/관계 참조 유지.
- 현재 Firestore `users/{uid}` Rules는 selectedPetId 필드를 허용하지 않아 **선택 프로필 값은 원본 Guest DataStore에만 보존**. FB-05에서 별도 스키마·Rules 계약 확정 뒤 서버 계정별 선택 설정 동기화.
- 이 PR은 **Firestore 초기 보관 기능**이지 양방향 동기화나 최초 로컬 계정 DB 복사는 아님. `migrationState=ready`는 첫 이행 본문·사진 검증이 완료됐다는 표기이며 FB-05의 동기화 완료와 다름.
- 로그인된 계정의 암호화 백업/복원은 FB-03 보호 정책에 따라 별도 구현 전 비활성.
- 실기기에서 개발 Firebase 실제 쓰기·조회가 성공했다는 증거는 현재 없음. 앱 UI를 통해 실제 로그인·명시적 백업 확인·승인해야만 실행됨.

## 5. QA·회귀 기준

- Unit: 0/1/1000 record payload mapping, UUID 유지, 숫자 0 vs null, 필드 길이 검증, 결정적 source hash, 미승인/변경 원본 재검증.
- Firebase Rules Emulator: 엄격한 Full Pet/Care 스키마 수락 및 revision=0 문서 재덮어쓰기 거부, 타 계정/비로그인 거부, 사진 5MiB 한도/삭제 거부.
- Android CI: `firebaseDev`에만 Firestore/Storage SDK 및 UI, `main` debug/release 동일 서명·패키지·로컬 복원 회귀 유지.
- Full emulator / API29·35·36 Guest/A/B 격리 및 Firebase 계정 화면 UI 회귀.
- 실제 Firebase 개발 프로젝트에 테스트 계정에서만 사전 샘플을 만들어 **0/1/1000 기록, 사진 유/무, 기존 클라우드 데이터, 프로세스 중단 후 재시도, 충돌 차단 및 원본 SHA** 확인. 실제 사용자 기록으로 자동 테스트 금지.
- PR CI는 가상 Firebase 설정·로컬 에뮬레이터를 사용하므로 원격 실데이터 접근/Google 계정 로그인 성공을 증명하지 않음.
